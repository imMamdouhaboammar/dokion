# M4 Readiness, Coverage, and Release Gates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Dokion compute an auditable readiness result from the exact approved playbook, declared coverage lanes, finding states, evidence, and release gates, without claiming readiness for undeclared or unverified work.

**Architecture:** Add focused applicability, coverage, completion, and release-gate evaluators that consume the loaded playbook and persisted run artifacts. The execution engine will invoke these evaluators after each step and at run completion, persist the result in `state.json`, and render the same result in `HARDENING.md`. Readiness is capped whenever blocking lanes are unassigned, platform degradations are present, required steps are incomplete, or blocking gates fail.

**Tech Stack:** Bun 1.3.14, TypeScript 7.0.2, JSON Schema draft 2020-12, Bun test, GitHub Actions.

## Global Constraints

- Capability selection, ordering, installation, substitution, and activation remain `USER_ONLY`.
- Detection may gate a declared step; it may never introduce an undeclared capability.
- Only `VERIFIED` findings count as repaired for release gates.
- Every readiness claim must reconcile exactly against the active playbook digest and current commit.
- Unassigned blocking lanes cap readiness at the playbook's `unassigned_lane_readiness_cap`.
- A failed blocking release gate prevents `READY_FOR_PRODUCTION`.
- No evaluator may mutate `.dokion/playbook.json` or infer new stages.
- Existing M0-M3 tests and strict TypeScript checks must remain green.
