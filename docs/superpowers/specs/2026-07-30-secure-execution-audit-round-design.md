# Dokion Secure Execution and Audit Round Design

**Date:** 2026-07-30
**Status:** Approved by direct execution instruction
**Baseline:** `a1e1d55`, Dokion 0.3.0, 199 tests passing
**Goal:** Close the next public-beta P0 gaps across capability provenance, contained command execution, reversible repair transactions, qualified readiness, and independent audit.

## Scope

This round implements CAP-005 through CAP-008, STATE-008 and STATE-009, EXEC-001 through EXEC-009, and EVID-001 through EVID-005 plus EVID-008 and EVID-010. It does not add assurance modules, seeded product journeys, adapter expansion, Windows promotion claims, or release publication changes.

## Architecture

The implementation is split into four bounded layers. Capability validation records provenance, validates declared environment prerequisites, detects conflicts, and feeds a deterministic read-only doctor report. Secure execution converts playbook commands into explicit command specifications, applies platform and environment policies, streams bounded evidence, and controls process trees. Repair safety uses canonical path decisions, bounded ignored and binary snapshots, side-effect checkpoints, and one transaction manifest per repair. Readiness and audit derive deterministic reports from persisted state and evidence and never infer success from model output.

## Authority and security invariants

- `.dokion/playbook.json` remains the only execution authority.
- No task may select, install, substitute, reorder, upgrade, or enable a capability.
- Read-only commands do not mutate project or Dokion state.
- Secret values are never persisted in state, evidence, reports, logs, or errors.
- Argument-vector commands bypass shell parsing. Legacy shell strings remain explicit higher-risk commands.
- Unsupported platform guarantees block or degrade explicitly. They are never silently bypassed.
- Every external side effect has an intent checkpoint and completion checkpoint.
- Every repair has one auditable transaction record and exact rollback proof where supported.
- Human and JSON readiness wording is generated by one qualified statement formatter.

## Verification gates

Every landed task must pass its focused test and `bun run typecheck`. Every integration wave must pass `bun test`, `bun run validate:contracts`, and `bun run build`. Final landing additionally requires `bun run validate:distribution` and `bun run smoke:package`.
